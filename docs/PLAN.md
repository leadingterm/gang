# Gang Implementation Plan

## 1. Architectural Pillars

1. **Compile-Time Plugins with Domain-Transparent Configuration**:
   - Core crates in Rings `0_kernel`, `1_domain_ports`, and `2_application` have **zero built-in cloud, database/SQL, TLS, storage, or action-isolation mechanics**.
   - Every backend is an independent Ring 3 plugin crate at **`tier: 30`** implementing `gang_spi::Plugin` and the ports of its domain. `gang-main` composes the plugins at compile time with `gang_spi::compose!`, which generates one typed configuration enum and one statically dispatched enum per domain. There is no runtime registry; adding a backend is a new crate plus one line in `compose!`.
   - **Plugin domains**: provisioner, cache, signer, scheduler, database, sandbox, identity provider, client authentication, worker authentication, and the optional action limits; the table is in SPECIFICATION §1.1.
   - **Transparent User Experience**: Users never see `"plugin"` or `"selection"` in configuration files or CLI flags. Each domain section (`[provisioner.aws]`, `[sandbox.bwrap]`, `[identity.providers.google.oidc]`) both activates that backend and supplies its strongly typed configuration; an unknown backend is a parse error.
   - **Mutual Isolation (`tier: 27-30`)**: All 13 Ring 3 crates share `ring: 3_driven_adapters`; eleven are at `tier: 30`: nine plugin crates (`gang-nativelink`, `gang-aws`, `gang-local`, `gang-oidc`, `gang-noop`, `gang-bwrap`, `gang-sqlite`, `gang-cgroup`, `gang-authn`) (a crate may provide plugins in several domains: `gang-aws` and `gang-local` each provide a provisioner, a cache, and a signer) and two fixed adapters (`gang-ui`, `gang-embed`). The fixed adapters `gang-mtls` (`tier: 27`) and `gang-tls` (`tier: 28`) are lower tiers, so plugins may depend on them (`gang-oidc` depends on `gang-tls`). A crate may depend only on crates at a lower tier, so no two tier-30 crates can depend on each other. Only `gang-main` (`tier: 45`) may import the plugin crates; the fixed adapters may also be imported by the Ring 4 library crates that need them (`tier: 40`).
   - **Pluggable Authentication, Separate Transport**: authentication is chosen per surface. Clients (people and CI) use `token`: a bearer ES256 JWT that Gang issues after an identity-provider proof and verifies locally. Build workers use `mtls`: a client certificate issued from a workload proof and verified against Gang's CA. `none` is available on either surface for trusted networks. Transport is a separate switch, `[server] transport`, which says whether Gang terminates TLS, so a tunnel can terminate it instead. NativeLink checks nothing itself; a per-request gate in front of it authenticates each call, refuses revoked principals, and applies the surface's admission rule.
   - **Deferred Beyond v1**: `gang-firecracker` (`[sandbox.firecracker]`), `gang-postgres` (`[database.postgres]`), `gang-saml` (a second identity provider plugin), and running actions under a separate uid from the worker (needs privilege; AWS hardening).
2. **Code & Structural Discipline**:
   - Rust Edition `2024`, toolchain `1.97.1` (NativeLink's `rust-version`) pinned through `rules_rust` in `MODULE.bazel`.
   - Single flat `src/*.rs` layer per crate; zero `#[path]` attributes; acyclic intra-crate module DAGs.
   - Pure-exports `src/lib.rs` facades (`//!` docs, inner attributes, `mod` declarations, and `pub use` re-exports only).
   - `unsafe_code = forbid` and `missing_docs = deny` live in `[workspace.lints]` of `Cargo.toml`, which Bazel reads per crate through rules_rust's `extract_cargo_lints`; system calls go through safe wrappers (`rustix`).
   - `std::rc::Rc`, `std::rc::Weak`, and `std::cell::RefCell` banned; zero `Arc<T>` on domain values; lexical `&mut self` state machines in Ring 2.
   - Strong types for configuration: durations (`"10m"`) parse into `std::time::Duration`, sizes (`"29GiB"`) into `gang_types::Bytes`, and names into newtypes.
   - Configurability: every behavioural tunable (timeouts, intervals, budgets, headroom, retry and refetch limits, grace periods, size caps, feature toggles) is a typed field of its owner's configuration section with a documented default; toggles are enums, not bools; no tunable value is hard-coded.
   - Enforced by rustc and Clippy under Bazel: Clippy's `pedantic`, `unwrap_used`, `expect_used` and `panic` lints are `deny` in `[workspace.lints]` (read by Bazel through `extract_cargo_lints`), and `.bazelrc` passes only `-Dwarnings` to `@rules_rust//rust/settings:clippy_flags`. `@rules_rust//rust/settings:clippy.toml` points to `//:clippy.toml`, whose `disallowed-types` bans the types above and std `Mutex`, `RwLock` and `Condvar` (use `parking_lot`). Bazel runs Clippy and rustfmt as tests (`rust_clippy_test`, `rustfmt_test`) generated by the workspace Rust macros. `bazel/architecture` checks ring/tier ordering, the flat `src/*.rs` layout, and pure `lib.rs` facades.

3. **Security**:
   - Live revocation: principal revocation applies to every plugin. A `revoked_at` flag in the principal registry is loaded into an in-memory set at start, and the gate checks it on every request and every issuance. Certificates are also revoked by serial, and `gang-tls` closes their established connections (`mtls` only). A stolen token is usable for at most `token_ttl`; there is no CRL file and no restart.
   - No stored secrets: developers hold their own login; CI jobs and workers use credentials their provisioner mints per job or per instance; the CA signing key lives in AWS KMS (`[signer.kms]`) and never exists on disk.
   - Loopback-only mock IMDS: `mock_imds_listen` must be a loopback address, and `gang.toml` parsing rejects any other. Each worker presents a per-instance secret; there are no sessions.
   - Key files are written atomically with mode `0600` (temp file, fsync, hard link) inside a `0700` directory owned by the running user, checked at start.
   - CAS input integrity: with `[execution] input_links = "break"`, `gang exec` gives each action private input inodes, so an action cannot alter a cached input that a later action sees (SPEC §3.7).
   - Bounded worker caches: the worker's fast CAS evicts against a budget derived from the scratch volume's capacity.
   - Per-action kernel limits: `gang-cgroup` bounds each action's memory, CPU, and process count and kills its leftovers on exit (SPEC §3.8).

### 2.1 Plugin Domains and Ports (`gang-spi`)

The plugin domains, their `gang.toml` sections, cardinality, plugins and ports are tabulated in SPECIFICATION §1.1.

The fixed adapters are imported by the Ring 4 crates that need them, by `gang-oidc` (`gang-tls`), and by `gang-main`.

## 3. Implementation Sequence

The reference environment is a Linux host (x86-64) where actions run under `bwrap`. Local Mode also runs on macOS with `noop`.

Gang builds with Bazel:
- Bazel `8.7.0` (`.bazelversion`), `rules_rust` `0.72.0` with the Rust `1.97.1` toolchain (glibc for build tools on the exec platform; the `x86_64`/`aarch64-unknown-linux-musl` targets for every Linux artifact) and the zig `linux_amd64`/`linux_arm64` C toolchains (glibc 2.31 for build tools, musl for artifacts), so the Linux `gang` binary is fully static.
- `crate_universe` `crate.from_cargo` over the root `Cargo.toml` + `Cargo.lock` (`Cargo.Bazel.lock`); Cargo manifests stay the source of truth for dependencies.
- Gazelle (`aspect_gazelle_prebuilt` with a Rust extension) generates every `BUILD.bazel`; `//:gazelle.check` fails on drift.
- Workspace macros in `bazel/rust/defs.bzl` (`workspace_rust_library`, `workspace_rust_binary`, `workspace_rust_proc_macro`) attach unit, Clippy, and rustfmt tests to every crate (libraries also get doc and integration tests) and declare each package's `workspace_sources`, which `workspace_rust_source_set` collects.
- `flake.nix` devShell provides `bazelisk` (the Bazel version is owned by `.bazelversion`) and `bubblewrap` (Linux).

NativeLink is embedded as a Rust library at its latest release, tag `v1.8.3`. `gang-nativelink` depends on `nativelink-config`, `-scheduler`, `-store`, `-service`, `-worker`, `-util`, `-error`, and `-proto` through Cargo git dependencies pinned to that tag (resolved by `crate_universe`) and reimplements only the glue of upstream `src/bin/nativelink.rs`: it builds the stores, scheduler, and services from typed `nativelink-config` values and serves them. NativeLink's `rust-version`, `1.97.1`, sets the workspace toolchain. There is no `nativelink` binary or process, no JSON5 configuration, and no admin HTTP API: the scheduler is called directly. `gang server` runs the controller through `SchedulerPort::run_controller` on connections it has accepted through `gang-tls`, and `gang worker` runs NativeLink's local worker through `SchedulerPort::run_worker`.

Every port trait and every domain lands with the foundation crates. Because `compose!` requires the nine mandatory domains (the optional `limits` domain may be omitted), Step 1 builds at least one plugin per mandatory domain, including `gang-sqlite` and `gang-oidc` (their full behaviour, ledger content, and verification stay in Step 2).

### Step 1: Local Vertical Slice on Linux and macOS
1. Scaffold `MODULE.bazel`, `.bazelversion`, `.bazelrc` (Clippy flags), `clippy.toml`, the Cargo workspace, Gazelle, `bazel/rust/defs.bzl`, `flake.nix`, and the decision records under `docs/adr`.
2. Implement the slice crates: `gang-clock`, `gang-types`, `gang-wire`, `gang-config`, `gang-macros`, `gang-spi`, `gang-reconciler`, `gang-authn`, `gang-nativelink`, `gang-local`, `gang-noop`, `gang-bwrap`, `gang-cgroup`, `gang-sqlite`, `gang-oidc`, `gang-exec`, `gang-worker`, `gang-server`, `gang-e2e`, and `gang-main`.
   - `gang-spi` + `gang-macros`: the `Plugin` contract, `compose!`, `#[port]`, and every port of every domain: provisioner (compute, lifecycle, scratch, workload credential), cache, signer, scheduler, database, sandbox, identity, and the optional action limits. All ports land in Step 1 with the foundation; Step 2 adds the plugins' real behaviour.
   - `gang-nativelink`: embeds NativeLink v1.8.3 (see above). `SchedulerPort::run_controller(spec, ControllerConnections)` builds the stores, the `historical_resource` scheduler, and the client and worker gRPC services from typed `nativelink-config` values and serves them over HTTP/2 on the already-accepted, already-authenticated connections it is handed (`BoxedConnection` streams); it contains no TLS, no revocation, and no listener addresses. `run_worker(spec)` runs NativeLink's local worker in process. `snapshot` and `set_draining` call the scheduler directly. `[scheduler.nativelink]` holds the dialable `worker_endpoint` URL, `scheduler_name`, `max_open_files`, and the NativeLink tuning; the public URL is the top-level `endpoint` (ADR-09's one public listener). `endpoints` returns the two dialable endpoints as `ControllerEndpoints`.
   - `gang-local`: the provisioner `Local` (`[provisioner.local]`), the cache `FilesystemCache` (`[cache.filesystem]`), and the signer `FileSigner` (`[signer.file]`). The provisioner launches detached `gang worker` processes (copies of the running `gang` binary) recorded under `state_dir`, tracks, and terminates them; each `gang worker` runs NativeLink's local worker in process through `SchedulerPort::run_worker`. Its mock IMDSv2 mints workload JWTs with a key under `state_dir` and serves OIDC discovery and JWKS on `mock_imds_listen`, which must be a loopback address; Local Mode lists `[identity.providers.local-workers.oidc]` and workers authenticate through `[authentication.workers.mtls]` as on `aws-workers`. Key files are written atomically with mode `0600` inside a `0700` directory owned by the running user, checked at start.
   - `gang-sqlite` and `gang-oidc`: one plugin each for the database and identity domains, so `compose!` covers all nine mandatory domains (`gang-local` supplies the provisioner, cache, and signer; `gang-authn` the client and worker authentication); their full behaviour is Step 2.
   - `gang-noop` and `gang-bwrap` behind `gang exec`, the worker `entrypoint`. `gang exec` applies `[execution] input_links` and the optional action limits before the sandbox (SPEC §3.7).
   - `gang-cgroup` (`[limits.cgroup]`, Linux): per-action cgroup v2 under the worker's delegated subtree (the worker in the leaf `worker/`, each action in `actions/<id>`): `memory.max` as a hard ceiling above NativeLink's soft memory enforcement, `memory.swap.max` from `swap_max` (default `0`), `memory.oom.group=1`, `cpu.max` from `cpu_count`, `pids.max`; `cgroup.kill` on exit, and `memory.peak` and `cpu.stat` recorded. Absent on macOS.
   - `gang-reconciler`: desired workers per fleet from queued demand, attributed to each action's candidate fleets in preference order. Scale-in drains a worker, then terminates it after `idle_timeout`. All state comes from NativeLink and the provisioner on every pass. Worker lifetime is not a reconciler input: it is the provisioner's `worker_lifetime` setting (§4). A Pending instance counts as capacity; an instance is an orphan only when it is InService without a worker for `boot_grace` since `launched_at`.
3. **Gate 1**: `bazel run //crates/gang-e2e:local -- --gate 1 --gang <path-to-gang>`, on Linux under `[sandbox.bwrap]` and on macOS under `[sandbox.noop]`; it runs the Gate 1 scenarios of SPECIFICATION §6.5.

### Step 2: Identity & State
1. `gang-sqlite` (`[database.sqlite]`): principal registry, issued-certificate ledger, and scaling audit log.
2. `gang-mtls`: Gang's certificate authority (CSR verification, X.509 worker certificates with SPIFFE IDs, server certificates for `gang server` and NativeLink), signing through `CertificateSignerPort` (`[signer.file]` of `gang-local` in this step). Client tokens are signed by the same authority key. It keeps no revocation list; revocation lives in `gang-authn` and `gang-tls`.
3. `gang-tls`: the fixed TLS transport for `[server] transport = "tls"`. The acceptor (TLS 1.3, `h2`, no session resumption so every connection re-verifies) verifies worker certificates against the CA on the worker listener. `gang-server` loads the `RevocationSet` from the principal registry at start and adds a principal or serial on every revocation: a new connection from a revoked principal or serial is refused, and an established `mtls` worker connection closes. A token client's established connection stays open, and its next request is refused by the gate. No CRL file and no restart.
4. `gang-oidc` (`[identity.providers.<name>.oidc]`): provider-agnostic OpenID Connect. Endpoints come from the issuer's discovery document; identity is a configured claim checked against configured claim requirements; nothing in the crate names a provider, domain, or organization. The examples use Google Workspace (`example.com`) as the developer provider and GitHub Actions (the `example-org` organization) as the CI provider. `gang login` starts a loopback server, prints the authorization URL, and opens it in the browser; the provider redirects back to the loopback server, or, on a remote machine, the user pastes the redirected `http://127.0.0.1:{port}/callback?...` URL at the prompt. CI jobs exchange their job token through `gang login --workload` (the `<owner>/gang/.github/actions/login` composite action on GitHub Actions).
5. `gang-client` (`gang get`, `gang bazelrc`): `gang get` is Bazel's credential helper. It prints the cached bearer token or mints a new one from the stored OIDC refresh token, so the identity provider re-approves the user whenever a new ID token is needed. `gang bazelrc` prints the static flags for a committed `.bazelrc`. The logic lives in `gang-client`, which `gang-main` calls for its client commands.
6. `gang-server`: the public listener (`listen`, port 443 in deployment) serves the Gang API, the dashboard and the REAPI services on one server that speaks HTTP/2 and HTTP/1.1. Each route is gated by the plugin of its surface: `POST /v1/session:authenticate` is the `token` client plugin's route, `POST /v1/certificates` is the `mtls` worker plugin's route, and the permission routes need a `[[server.roles]]` permission. [`docs/API.md`](./API.md) is the reference for every route. The private `worker_listen` is gated by `mtls`. The NativeLink controller runs in process and the reconciler control loop drives it.
7. **Gate 2**:
   - Run `bazel run //crates/gang-e2e:local -- --gate 2 --gang <path-to-gang>`, which runs Gate 1 and every scenario whose first gate is two (`Scenario::gate`). CI runs the additions alone with `--gate 2 --additions`.
   - `gang login` against the configured developer provider (Google Workspace in the example) yields a bearer token that the public listener accepts, both through the browser redirect on the same machine and by pasting the redirect URL over SSH.
   - Bazel over `grpcs://` succeeds with that token and is rejected without one.
   - `gang get` reuses the cached token until it nears expiry, then mints a new one.
   - Once the identity provider refuses the refresh, `gang get` fails and a browser login is required.
   - A revoked principal is refused on new connections and requests. Its established `mtls` worker connections close; a token client's open connection stays up and its next request is refused. `gang restore --principal` admits it again, all without a restart.
   - A GitHub Actions job in an `example-org` repository obtains a token through `gang login --workload --token-command` and runs a remote Bazel build; a job token from another organization is refused.

### Step 3: AWS Provisioner, Cache, and Signer
1. `gang-aws`: the provisioner `Aws` (`[provisioner.aws]`: EC2 Spot ASG compute, warm pool release, on-demand fallback group, IMDSv2 lifecycle, scratch adoption, STS workload credentials), the cache `S3Cache` (`[cache.s3]`), and the signer `KmsSigner` (`[signer.kms]`). The plugin adopts the scratch volume that a root `gang-scratch.service` prepared on the instance-store NVMe (RAID0, XFS with reflink) and never formats or mounts it. The worker's fast CAS and work directories live on that volume, so `input_links = "break"` replaces a hard link by a reflink.
2. **Gate 3**:
   - Per-plugin unit and shared port-compliance suites pass.
   - The end-to-end harness (`bazel run //crates/gang-e2e:local -- --gang <path-to-gang>`) additionally covers a simulated Spot interruption mid-action once the AWS deployment is wired to it.
   - A worker obtains its certificate from an STS web identity token, and `gang server` signs only through KMS.
   - The real-AWS confirmations ADR-22 I1-I5 and ADR-23 I6-I9 (SPECIFICATION §3.1) pass on a deployed fleet.

### Step 4: NixOS AMIs & Terraform Modules (`infra/*`)
1. ### Step 5: Operator Dashboard (ADR-25 to ADR-31)
1. The live state and its API:
   - `gang-wire` defines the state schema (`State`, `Delta`, `Session`, the principal and role bodies), `gang-reconciler` exposes the per-fleet outlook and the typed cause of every step, and `gang-state` derives each frame from one control pass, diffs frames into deltas and encodes the SSE events.

2. Browser access: `gang-authn` mints and accepts session tokens from the session cookie, `gang-oidc` accepts a dedicated Web-application client (`additional_audiences`, the login client override), `gang-server` serves `GET /v1/session` and mounts `/ui/login`, `/ui/callback` and `/ui/logout` under `[dashboard.login]`, `gang-tls` and `gang-nativelink` serve HTTP/1.1 on the public listener.
3. The bundle: the TypeScript sources in `ui/` build to `//ui:dist`, `gang-embed` generates the asset table, and `gang-ui` serves it under `/ui` through the `Gateway` of `gang-server`. `gang local up --insecure` binds the `administrator` role to `none:anonymous` and prints the dashboard URL.
4. **Gate 5**:
   - `bazel test //...` passes, which includes the unit and integration tests of `gang-state` (golden frames shared with the `ui/fixtures` recordings, and a `diff`/`apply` round trip), `gang-ui` (headers, encoding negotiation, and an embedded table equal to `//ui:dist`), `gang-embed`, `gang-server` (the stream, the hub, the gate and the sign-in routes), and `//ui/...` (`tsc --strict`, the store, client and view tests, and the bundle budgets).
   - `gang local up --insecure` prints the field `ui` with `<endpoint>/ui/`; the page loads, `GET <endpoint>/v1/state` answers the snapshot, and `GET <endpoint>/v1/state:watch` sends a `snapshot` event, then `delta` and `tick` events while a build scales the fleet `0 -> 1 -> 0`.
   - In a deployment that sets `[dashboard.login]`, a principal whose role grants `state.read` signs in through the identity provider and sees the state, and the stream ends with `closed: EXPIRED` when the session expires.

## 4. Future Provisioners

A new provisioner is a Ring 3 plugin crate at `tier: 30` and one line in `compose!`. It reuses the `cache` and `signer` domains as they are (`[cache.s3]` and `[signer.kms]`). It implements `ProvisionerPort` over `&Fleet`: `set_desired_capacity` raises instances up to `desired` and never removes any; `terminate` is idempotent (`Ok` when the instance is already gone) and cancels a Pending instance; a Pending instance counts as capacity however long it waits, never as an orphan. It sets its default `worker_lifetime`.

- **Kubernetes** (`gang-kubernetes`, `[provisioner.kubernetes]`):
  - Compute: one pod per worker, with one pod template per fleet, each placed by `nodeSelector` on its fleet's ISA architecture.
  - Worker lifetime: `single_use` by default, so each pod runs one action and exits (NativeLink `single_use`); `worker_lifetime = "long_lived"` in `[provisioner.kubernetes]` overrides it.
  - Identity: the pod's projected service-account token is the workload credential, verified by an OIDC identity provider entry (`[identity.providers.<name>.oidc]`) against the cluster's issuer.
  - Limits: pod-level resource requests and limits bound each pod, so no `[limits.<plugin>]` section is used.
  - Sandbox: `noop` where the cluster blocks user namespaces, with the pod as the isolation boundary; `bwrap` otherwise.
  - Cache and signer: `[cache.s3]` and `[signer.kms]`.
- **Slurm** (`gang-slurm`, `[provisioner.slurm]`):
  - Compute: `sbatch` jobs that each run `gang worker`; scale-in with `scancel`.
  - Worker lifetime: `long_lived` by default; `single_use` is available through `worker_lifetime`.
  - Lifecycle: `--signal` before the job is preempted or reaches its time limit delivers the preemption notice to `gang worker`.
  - Limits: Slurm job cgroups bound each job, so no `[limits.<plugin>]` section is used.
  - Identity: the job's workload credential is a proof of the provider that `[authentication.workers.mtls]` names; `gang worker` presents it to `POST /v1/certificates` and receives its certificate, as on the other provisioners.
  - Cache and signer: `[cache.s3]` and `[signer.kms]`, or the filesystem and file plugins on a shared filesystem.

### Platform mapping

| | AWS | Kubernetes | Slurm |
|---|---|---|---|
| Instance | EC2 in ASG `fleet.name` | pod labelled `gang/fleet=<name>` | one job, `--comment gang:<name>` |
| `InstanceId` | EC2 id | pod name | `{cluster}-{jobid}` |
| Pending | ASG Pending | phase Pending | PD, CF |
| InService, `launched_at` | InService, LaunchTime | Running, container `startedAt` | R, StartTime |
| Terminating | terminating states | Succeeded, Failed, `deletionTimestamp` | CG; finished jobs vanish |
| `terminate` | `TerminateInstanceInAutoScalingGroup` with decrement, or a release to the warm pool (ADR-22) | delete pod (idempotent) | `scancel` |

`supply()` reads platform state every pass, so no fleet state is persisted (SPECIFICATION §5).

### Worker identity

No stored secrets; `Proof` stays opaque and the proof ports are unchanged (ADR-07).

| Platform | Worker presents | Verified by |
|---|---|---|
| AWS | STS `GetWebIdentityToken` | `gang-oidc` |
| Kubernetes | projected service-account token, `aud = workload_token.audience`, re-read per call | `gang-oidc` against the cluster issuer |
| Slurm | `munge -n -s <jobid>` | a `slurm` identity plugin (`gang-slurm`) |
| Local | mock-IMDS JWT | `gang-oidc` |

- **Kubernetes.** `principal_claim = "sub"` yields the service account, which all pods share, as the shared IAM role does on AWS.
- **Slurm.** `unmunge` gives single use per credential. `squeue` must show the job RUNNING on the credential's host, owned by the submit user, with comment `gang:<fleet>`. The principal is `slurm:{cluster}:{jobid}`.
- **Sandbox.** `noop` is for environments where the pod, job or host already isolates the worker: macOS Local Mode, Kubernetes pods, HPC jobs. Such environments omit `[limits.cgroup]`, and `input_links = "break"` is pointless for single-use workers.

### Per-action cost

A single-use worker starts every action with a cold fast CAS and a fresh certificate: one KMS signature and one ledger row per action, and S3 reads in place of a local CAS cache. Bursts of hundreds of pods stress KMS rate limits (ADR-13). A site without KMS has only `signer.file`, which stores a key on disk, until `signer.pkcs11` or `signer.vault` exists.

### Deferred

- Plugins: `gang-kubernetes`, `gang-slurm`, `signer.pkcs11`, `signer.vault`, `gang-fs`; Slurm minted-JWT identity with a shared JWT-issuer crate.
- `gang-oidc` nested claims and CA or JWKS files; `issuance = "once"` per identity provider, enforced through the ledger; `cache.s3` `access = "via_controller"` and `endpoint`; SAN aliases on `worker_endpoint`; pod size classes; a `reflink` flag on `MountedScratchVolume`; a timeout for Pending instances.
